What Is a Knowledge Graph?

A knowledge graph (KG) is a structured, semantically-rich network that encodes real-world knowledge as entities (nodes) and relationships (edges). Unlike flat tables, KGs store meaning — not just data. Google's Knowledge Graph, Wikidata, and DBpedia are landmark examples. For AI agents, a KG acts as a shared, traversable long-term memory enabling multi-hop reasoning: "What tasks used Tool X in Session Y that also produced Concept Z?" — impossible in a vector DB alone.

💡A relational DB stores data. A vector DB stores similarity. A knowledge graph stores meaning. The ideal AI memory system is a hybrid of all three — exactly what Neo4j's vector index + LightRAG enable in L.O.R.A.

Core Anatomy
Nodes (Entities)

Real-world objects, concepts, or events. Each has a label (its type) and properties (attributes).
(:Concept {name:"Transformer", domain:"DL"})

Edges (Relations)

Directed, typed connections. Edges are first-class citizens with their own labels, directions, and properties.
-[:DISCOVERED {confidence:0.95}]->

Properties

Key-value metadata on nodes and edges. Strings, numbers, dates, lists. Indexed for fast lookup. Never encode structural meaning in properties — use edges.

Four Types of Knowledge to Store in L.O.R.A.
Episodic Memory

Events, sessions, tasks, agent actions, conversation history. "Agent X ran Task Y at time T and produced Output Z." Stored with timestamps and session IDs on edges.

Semantic Memory

Facts and domain knowledge extracted from research. "Transformers use attention. Attention is O(n²) in sequence length." Extracted via LLM and stored as entity-relation triples.

Procedural Memory

Code snippets, workflows, tested procedures. "To deploy FastAPI with Docker, use this Dockerfile." Stored with success/failure counts so agents learn what works.

Agent State & Plans

Current goals, pending tasks, dependencies, capability maps. The Orchestrator reads this to plan. "Task A depends on Task B. Code Agent has tools: python_exec, git, docker."

Ontologies — Giving Your KG a Schema

An ontology is a formal specification of the types of entities, relationships, and constraints in your knowledge domain. Without an ontology, your KG is a bag of random triples. With one, it becomes a reasoned knowledge system. For L.O.R.A., the ontology defines: what node labels exist, which edge types connect which node types, what properties are required vs optional, and which properties are unique (constraints). The ontology is your contract — agents write to it, queries rely on it.

TBox (Schema Layer)

The "terminological box" — class definitions, property types, cardinality rules. Equivalent to a DB schema. In Neo4j: CREATE CONSTRAINT FOR (c:Concept) REQUIRE c.name IS UNIQUE. Define this before any data enters. Prevents duplicate nodes and enforces data integrity across all agents.

ABox (Instance Layer)

The "assertional box" — actual data instances conforming to the TBox. Every node an agent creates is an ABox assertion. In RDF these are rigorously separated layers; in Neo4j you blend them pragmatically. All agent-written nodes, relationships, and properties live here.

RBox (Inference Rules)

Role axioms — "if A KNOWS B and B KNOWS C, infer A KNOWS C transitively." In Neo4j, encode as Cypher inference queries or use APOC triggers to fire on write. Critical for agent capability inference: if Code Agent USES Docker and Docker RUNS Python, infer Code Agent CAN_EXECUTE Python.

🏗️L.O.R.A. ontology principle: model the domain, not the implementation. Don't create :APICall nodes — create :Action nodes with a type property. Your ontology should stay stable even as agent capabilities grow. New agents just add new :Agent nodes and :Tool relationships — the schema never changes.

Indexing Strategies — Making KG Queries Fast

A KG with millions of nodes is useless if queries take seconds. Neo4j offers four index types. In L.O.R.A. you use all four for different access patterns. Missing an index means a full node scan — catastrophic at scale.

B-Tree Index (Default)

Auto-created by constraints; manually created with CREATE INDEX FOR (n:Label) ON (n.property). Best for equality lookups, range queries, and ORDER BY. Use on: name, id, status, created_at. Essential for all MERGE-based upserts — without it, every MERGE does a full scan.

Vector Index (HNSW)

Hierarchical Navigable Small World graph for approximate nearest neighbor search. Created with CREATE VECTOR INDEX concept_emb FOR (n:Concept) ON (n.embedding) OPTIONS {indexConfig:{`vector.dimensions`:768, `vector.similarity_function`:'cosine'}}. Requires all vectors to be the same dimension. Powers semantic retrieval.

Full-Text Index (Lucene)

Lucene-backed BM25 text search. CREATE FULLTEXT INDEX concept_text FOR (n:Concept) ON EACH [n.description, n.name]. Use for exact keyword search when semantic search over-retrieves. Especially valuable for named-entity lookup: agent names, tool names, project names.

Composite Index

Index on multiple properties: CREATE INDEX FOR (t:Task) ON (t.status, t.priority). Dramatically speeds up filtered queries like "all pending high-priority tasks." The left-most property must match for the index to be used — order matters.

History of Knowledge Graphs

Understanding the lineage of KGs clarifies why they're designed the way they are — and why they're the right substrate for AI agents in 2025.

1960s
Semantic Networks
Ross Quillian's associative memory models — nodes connected by typed arcs representing conceptual relationships. The conceptual ancestor of all KGs. No formal semantics, just intuitive graph structure for psychological modeling.
1984
CYC Project
Doug Lenat's attempt to encode all common-sense human knowledge. 1.5M assertions, 500k concepts, 30 years of work. Too rigid and brittle for modern AI — but proved machine-readable world knowledge is possible and valuable.
2001
Semantic Web / OWL
Tim Berners-Lee's vision: RDF + OWL + SPARQL for a web of linked, machine-readable data. Technically powerful with formal reasoning but developer-hostile (URIs everywhere, namespace management). Gave us Wikidata, DBpedia, LinkedGeoData.
2010
Freebase & Property Graphs
Google acquired Freebase (2010), Wikidata launched (2012) as community successor — now 110M+ items. Simultaneously, Neo4j's property graph model gained traction: edges as first-class citizens with properties, Cypher query language, developer-friendly.
2012
Google Knowledge Graph
The "Knowledge Graph" brand goes mainstream. Powers Google's entity cards and answer boxes. 500B+ facts. Spawned the entire industry term. Built on property graph principles with custom engineering at Google scale.
2020
Enterprise KGs
JP Morgan, Airbnb, LinkedIn, Uber adopt KGs for product recommendations, fraud detection, knowledge management. KGs prove their value in production at scale — not just research projects.
2024+
LLM + KG Fusion Era
GraphRAG (Microsoft), LightRAG, KG²RAG, HippoRAG emerge. LLMs extract KG triples from unstructured text at scale. KGs ground LLMs with verifiable, structured facts. Neo4j adds native vector indexes. The era of agentic KG systems — exactly what L.O.R.A. is built on.

Step 2 — Python KG Client
# core/kg_client.py
        from neo4j import GraphDatabase
        from typing import List, Dict
        
        class KGClient:
            def __init__(self, uri="bolt://localhost:7687",
                         user="neo4j", pwd="lorapassword"):
                self.driver = GraphDatabase.driver(uri, auth=(user, pwd))
        
            def upsert_entity(self, label: str, props: dict):
                with self.driver.session() as s:
                    s.run(f"""MERGE (e:{label} {{name: $name}})
                        SET e += $props, e.updated_at = timestamp()""",
                        name=props['name'], props=props)
        
            def upsert_relation(self, subj: str, pred: str,
                                 obj: str, props: dict = {}):
                with self.driver.session() as s:
                    s.run(f"""MATCH (s {{name:$s}}),(o {{name:$o}})
                        MERGE (s)-[r:{pred.upper()}]->(o)
                        SET r += $props""",
                        s=subj, o=obj, props=props)
        
            def vector_search(self, embedding: List[float],
                              top_k: int = 5, index="concept_embeddings"):
                with self.driver.session() as s:
                    result = s.run("""CALL db.index.vector.queryNodes(
                        $idx, $k, $emb) YIELD node, score
                        RETURN node.name, node.description, score""",
                        idx=index, k=top_k, emb=embedding)
                    return [dict(r) for r in result]
        
            def neighborhood(self, name: str, depth: int = 2):
                """Multi-hop neighborhood for graph context"""
                with self.driver.session() as s:
                    return s.run(
                        "MATCH p=(n {name:$n})-[*1..$d]-(m) RETURN p LIMIT 50",
                        n=name, d=depth).data()PYTHON

Step 4 — LLM Entity Extraction
# core/extractor.py — LLM-powered KG extraction
        import json
        from groq import Groq
        
        PROMPT = """Extract entities and relationships from the text.
        Return ONLY valid JSON — no markdown, no preamble:
        {
          "entities": [
            {"name":"str","type":"Concept|Task|Tool|Agent",
             "description":"brief description"}
          ],
          "relations": [
            {"subject":"name","predicate":"RELATION_TYPE",
             "object":"name","confidence":0.9}
          ]
        }
        Predicates must be UPPER_SNAKE_CASE.
        Text: {text}"""
        
        def extract_graph(text: str, client: Groq) -> dict:
            resp = client.chat.completions.create(
                model="llama-3.3-70b-versatile",
                messages=[{"role":"user",
                            "content":PROMPT.format(text=text)}],
                response_format={"type":"json_object"}
            )
            return json.loads(resp.choices[0].message.content)
        
        def ingest_text(text: str, kg, embed_fn, llm) -> int:
            """Chunk → extract → embed → store. Returns entity count."""
            chunks = [text[i:i+1000] for i in range(0, len(text), 800)]
            total = 0
            for chunk in chunks:
                data = extract_graph(chunk, llm)
                for ent in data['entities']:
                    ent['embedding'] = embed_fn(ent['description'])
                    kg.upsert_entity(ent['type'], ent)
                for rel in data['relations']:
                    kg.upsert_relation(
                        rel['subject'], rel['predicate'],
                        rel['object'], {'confidence':rel['confidence']})
                total += len(data['entities'])
            return totalPYTHON

Step 5 — Hybrid Retrieval in Practice

Pure vector search misses graph structure. Pure graph traversal misses semantic similarity. Hybrid retrieval combines both in a single query pass — the secret behind L.O.R.A.'s retrieval quality. The key insight: vector search finds the entry nodes, graph traversal expands from them into contextually connected knowledge.

# core/hybrid_retrieval.py — The retrieval core of L.O.R.A.
class HybridRetriever:
    def retrieve(self, query: str, depth: int = 2, k: int = 5) -> dict:
        # Step 1: embed the query
        emb = self.embed(query)

        # Step 2: vector ANN — find top-k semantically similar nodes
        vec_hits = self.kg.vector_search(emb, top_k=k)

        # Step 3: full-text BM25 — catch exact keyword matches
        txt_hits = self.kg.fulltext_search(query, top_k=k)

        # Step 4: graph expansion — walk depth hops from entry nodes
        seeds = {h["node.name"] for h in vec_hits + txt_hits}
        graph_ctx = []
        for seed in list(seeds)[:3]:  # expand top 3 seeds only
            graph_ctx.extend(self.kg.neighborhood(seed, depth=depth))

        # Step 5: rerank by relevance score
        all_nodes = self._deduplicate(vec_hits + txt_hits + graph_ctx)
        return self._rerank(all_nodes, query, emb)

    def fulltext_search(self, query: str, top_k: int = 5):
        with self.driver.session() as s:
            return s.run("""CALL db.index.fulltext.queryNodes(
                'concept_text', $q) YIELD node, score
                RETURN node.name, node.description, score
                ORDER BY score DESC LIMIT $k""",
                q=query, k=top_k).data()PYTHON

Step 7 — Entity Canonicalization

Raw LLM extraction produces noisy, inconsistent entity names: "React.js", "ReactJS", "React Framework", "React" all refer to the same thing. Without canonicalization, your KG fragments into disconnected duplicate nodes. Canonicalization is the process of merging these into a single authoritative node.

# core/canonicalizer.py — Merge duplicate entities
class EntityCanonicalizer:
    def __init__(self, kg, embed_fn, llm, threshold=0.92):
        self.kg = kg
        self.embed = embed_fn
        self.llm = llm
        self.threshold = threshold  # cosine sim above this = same entity

    def resolve(self, name: str, label: str) -> str:
        """Returns canonical name — existing or new."""
        emb = self.embed(name)
        candidates = self.kg.vector_search(emb, top_k=3, label=label)

        for c in candidates:
            if c["score"] > self.threshold:
                # High confidence: same entity, return canonical name
                return c["node.name"]
            elif c["score"] > 0.80:
                # Ambiguous: ask LLM to adjudicate
                verdict = self.llm.are_same_entity(name, c["node.name"])
                if verdict:
                    return c["node.name"]  # merge into existing

        return name  # genuinely new entity

    def merge_duplicates(self):
        """Cypher: redirect all edges from alias to canonical, delete alias."""
        with self.kg.driver.session() as s:
            s.run("""MATCH (alias:Concept)-[:ALIAS_OF]->(canon:Concept)
                CALL apoc.refactor.mergeNodes([canon, alias],
                    {properties:'discard', mergeRels:true})
                YIELD node RETURN node.name""")PYTHON
Step 8 — Memory Decay & Importance Scoring

Not all knowledge should persist forever. A KG that only grows eventually becomes noisy — old, irrelevant facts crowd out recent ones. L.O.R.A. implements a memory decay system inspired by human cognitive models: important, frequently-accessed memories persist; rarely-accessed, low-confidence ones fade. Decay runs as a background job.

Importance Score Formula

Each node gets a dynamic importance score:
importance = (access_count * 0.4) + (recency_score * 0.3) + (centrality * 0.2) + (confidence * 0.1)
This runs on a cron schedule. Nodes below threshold get their edges pruned first, then the node itself if isolated.

Decay Function

Exponential decay with half-life configurable per node type: score *= e^(-λt). Session nodes decay fastest (λ=0.1, 7-day half-life). Concept nodes decay slowly (λ=0.01, 69-day half-life). Pinned nodes never decay. Critical for preventing KG bloat.

# core/memory_manager.py — Decay scheduler
import math
from datetime import datetime, timedelta

class MemoryManager:
    DECAY_RATES = {
        "Session"  : 0.10,  # half-life ~7 days
        "Task"     : 0.03,  # half-life ~23 days
        "Concept"  : 0.01,  # half-life ~69 days
        "Document" : 0.005, # half-life ~138 days
        "CodeSnippet":0.002  # ~346 days — code persists
    }

    def run_decay_cycle(self):
        for label, lam in self.DECAY_RATES.items():
            with self.kg.driver.session() as s:
                s.run(f"""MATCH (n:{label})
                    WHERE n.pinned IS NULL
                    SET n.importance = n.importance * exp(-$lam *
                        duration.inDays(n.last_accessed, date()).days)
                    WITH n WHERE n.importance < 0.05
                    DETACH DELETE n""", lam=lam)PYTHON
🔒Pinning critical nodes: Set n.pinned = true on any node you never want decayed — your core ontology concepts, the agent registry, active project nodes. The decay function skips all pinned nodes. Use MATCH (n:Concept {name:"Transformer"}) SET n.pinned=true to protect foundational knowledge.

Community Detection for Topic Clustering

As your KG grows, you need a way to partition it into meaningful sub-graphs so retrieval doesn't search everything. Community detection automatically finds dense clusters of highly-connected concepts — these become your "topic partitions." L.O.R.A. runs Louvain community detection weekly and stores community IDs on nodes, so agents can pre-filter by community before vector search.

# core/community_manager.py — Topic clustering
class CommunityManager:
    def detect_and_store(self):
        """Run Louvain, write community IDs back to KG."""
        with self.driver.session() as s:
            # Project graph into GDS memory
            s.run("""CALL gds.graph.project('kg_proj',
                'Concept',
                {RELATES_TO: {orientation:'UNDIRECTED'}})""")

            # Run Louvain, write communities back
            s.run("""CALL gds.louvain.write('kg_proj',
                {writeProperty: 'community_id'})
                YIELD communityCount, modularity""")

            # Generate LLM summary for each community
            comms = s.run("""MATCH (n:Concept)
                RETURN n.community_id AS cid,
                       collect(n.name)[..10] AS names
                ORDER BY cid""").data()

            for c in comms:
                label = self.llm.label_community(c["names"])
                s.run("""MATCH (n:Concept {community_id:$cid})
                    SET n.community_label = $label""",
                    cid=c["cid"], label=label)

    def search_in_community(self, query_emb, community_label: str):
        """Partition-aware retrieval — 10x faster on large KGs."""
        with self.driver.session() as s:
            return s.run("""MATCH (n:Concept {community_label:$lbl})
                CALL db.index.vector.queryNodes('concept_embeddings', 5, $emb)
                    YIELD node, score WHERE node = n
                RETURN n.name, score ORDER BY score DESC""",
                lbl=community_label, emb=query_emb).data()PYTHON
KG-Grounded Generation — Preventing Hallucination

Standard LLMs hallucinate because they generate from parametric memory alone. When L.O.R.A. answers a query, it grounds the LLM's response in explicit KG facts. The retrieved nodes and relationships are injected into the prompt as structured context, and the LLM is instructed to cite node names. This makes answers verifiable and auditable.

# core/grounded_generator.py
GROUNDED_PROMPT = """You are L.O.R.A., an AI assistant with access to a verified knowledge graph.
Answer the question using ONLY the provided KG context.
If the answer is not in the context, say "Not in knowledge base."
Do NOT add information from general training.
Cite the node names you used in [brackets].

KG Context:
{context}

Question: {question}"""

async def grounded_answer(question: str, retriever, llm) -> dict:

    ctx_text  = format_for_prompt(ctx_nodes)
    answer    = await llm.complete(
        system=GROUNDED_PROMPT.format(context=ctx_text, question=question),
        user=question)
    return {"answer": answer, "sources": [n["name"] for n in ctx_nodes]}PYTHON

Agent Communication Protocol

Agents in L.O.R.A. don't communicate through message queues or direct function calls — they communicate via the Knowledge Graph. This is the most important architectural decision: the KG is not just storage, it's the communication bus. When Agent A finishes a task, it writes a node to the KG. Agent B reads that node as context. No shared state, no race conditions, full auditability.

Write Protocol (Agent → KG)

Every agent action writes a structured result node:
MERGE (r:Result {id:$id}) SET r.agent=$agent, r.output=$out, r.status="done", r.ts=timestamp()
This is the agent's "return value" — durable, queryable, cross-session.

Read Protocol (KG → Agent)

Before any task, agents pull relevant context:
MATCH (t:Task {id:$id})-[:DEPENDS_ON]->(dep) MATCH (dep)-[:PRODUCED]->(r:Result) RETURN r.output
Dependency outputs are always available — even if produced in a previous session.

Inter-Agent Task Dependency Graph (DAG)

The Orchestrator doesn't just assign tasks sequentially — it builds a Directed Acyclic Graph (DAG) of task dependencies. Tasks with no dependencies run in parallel. Tasks that depend on prior outputs wait. This is how L.O.R.A. achieves concurrency without race conditions — the KG enforces the ordering.

# core/dag_executor.py — Parallel DAG execution
import asyncio
from collections import defaultdict

class DAGExecutor:
    async def execute(self, steps: list, agents: dict) -> dict:
        # Build dependency map
        deps = {s["id"]: set(s.get("depends_on", [])) for s in steps}
        completed = {}

        while len(completed) < len(steps):
            # Find steps whose all dependencies are done
            ready = [s for s in steps
                      if s["id"] not in completed
                      and deps[s["id"]].issubset(completed)]

            # Run ready steps in parallel
            tasks = [agents[s["agent"]].run(s["task"],
                context={d:completed[d] for d in deps[s["id"]]})
                for s in ready]

            results = await asyncio.gather(*tasks)
            for step, result in zip(ready, results):
                completed[step["id"]] = result
                self.kg.write_result(step, result)  # persist to KG

        return completedPYTHON
Agent Design Patterns

Each specialized agent in L.O.R.A. follows a consistent design pattern that makes them composable, testable, and KG-aware. Every agent inherits from BaseAgent which wires in the KG client, LLM router, and logging hooks automatically.

# agents/base_agent.py — All agents inherit this
from abc import ABC, abstractmethod
import time, uuid

class BaseAgent(ABC):
    def __init__(self, kg, llm, name: str):
        self.kg   = kg    # KGClient — read/write Neo4j
        self.llm  = llm   # LLMRouter — waterfall providers
        self.name = name  # Unique agent identifier
        self._register()  # Write self to KG agent registry

    def _register(self):
        self.kg.upsert_entity("Agent", {
            "name": self.name,
            "capabilities": self.capabilities(),
            "status": "online",
            "last_seen": int(time.time())
        })

    async def run(self, task: str, context: dict = {}) -> str:
        task_id = str(uuid.uuid4())
        self.kg.upsert_entity("Task", {
            "id": task_id, "title": task[:120],
            "status": "running", "agent": self.name
        })
        try:
            result = await self._execute(task, context)
            self.kg.upsert_relation(self.name, "EXECUTED", task_id,
                {"status": "success", "ended_at": int(time.time())})
            return result
        except Exception as e:
            self.kg.upsert_relation(self.name, "EXECUTED", task_id,
                {"status": "failed", "error": str(e)})
            raise

    @abstractmethod
    async def _execute(self, task: str, context: dict) -> str:
        ...

    @abstractmethod
    def capabilities(self) -> list[str]:
        ...PYTHON

# voice/pipeline.py
        from faster_whisper import WhisperModel
        from kokoro import KPipeline
        import numpy as np
        import sounddevice as sd
        import asyncio
        
        class VoicePipeline:
            def __init__(self, orchestrator):
                self.orch = orchestrator
                self.stt  = WhisperModel("base.en", compute_type="int8")
                self.tts  = KPipeline(lang_code='a')   # 'a'=American English
                self.sr   = 16000
                self.wake = "lora"
        
            def record(self, secs=4) -> np.ndarray:
                audio = sd.rec(int(secs * self.sr),
                                samplerate=self.sr,
                                channels=1, dtype='float32')
                sd.wait()
                return audio.flatten()
        
            def transcribe(self, audio: np.ndarray) -> str:
                segs, _ = self.stt.transcribe(
                    audio, beam_size=5,
                    vad_filter=True,      # silero VAD baked in
                    vad_parameters=dict(min_silence_duration_ms=500)
                )
                return " ".join(s.text.strip() for s in segs)
        
            def speak(self, text: str, voice="af_bella"):
                for samples, sr, _ in self.tts(text, voice=voice):
                    sd.play(samples, sr)
                    sd.wait()
        
            async def run_loop(self):
                print("🎙️ L.O.R.A. listening for wake word...")
                while True:
                    audio = self.record(2)                   # short poll
                    text  = self.transcribe(audio).lower()
        
                    if self.wake in text:
                        self.speak("Yes?")
                        cmd = self.transcribe(self.record(7))
                        if cmd.strip():
                            resp = await self.orch.handle(cmd)
                            self.speak(resp)
        
                    await asyncio.sleep(0.05)PYTHON

"Brain for the OS" — The Always-On Reasoning Loop

The most ambitious part of this project: making L.O.R.A. feel like it's aware of what's happening on your machine, not just a chatbot you summon. This is achieved with a low-frequency background loop that periodically samples system state, screen content, and active windows — but writes only meaningful changes to the KG to avoid flooding it. The Reasoning Agent reviews this stream periodically and can proactively surface insights.

# core/brain_loop.py — The ambient awareness loop
import asyncio, hashlib

class BrainLoop:
    def __init__(self, os_agent, kg, reasoning_agent, interval=30):
        self.os    = os_agent
        self.kg    = kg
        self.brain = reasoning_agent
        self.interval = interval  # seconds between samples
        self._last_hash = None

    async def run(self):
        while True:
            state = self.os.status()
            active_win = self.os.active_window_title()
            fingerprint = hashlib.md5(
                f"{active_win}{state['cpu']>80}".encode()).hexdigest()

            # Only write to KG if context meaningfully changed
            if fingerprint != self._last_hash:
                self.kg.upsert_entity("SystemState", {
                    "ts": int(time.time()),
                    "active_window": active_win,
                    "cpu": state["cpu"],
                    "ram": state["ram"]
                })
                self._last_hash = fingerprint

                # Trigger proactive reasoning every ~10 changes
                if self.kg.count("SystemState") % 10 == 0:
                    insight = await self.brain.reason(
                        "Based on recent system activity, is there"
                        " anything the user might want help with?")
                    if insight.actionable:
                        self.os.notify("L.O.R.A.", insight.message)

            await asyncio.sleep(self.interval)PYTHON
⚠️Privacy by design: The brain loop NEVER sends screen captures or window titles to cloud LLMs by default — only the local Ollama model processes ambient state. Cloud providers (Groq, Gemini) are only invoked when the user explicitly asks a question. Add a privacy_mode flag that disables the brain loop entirely for sensitive work sessions.

Bootstrap Entry Point
# main.py — Start L.O.R.A. with one command: python main.py
        import asyncio
        from rich.console import Console
        from core.kg_client   import KGClient
        from core.llm_router  import LLMRouter
        from core.orchestratorimport Orchestrator
        from agents import (ResearchAgent, CodeAgent, DockerAgent,
            DatabaseAgent, GitAgent, FileAgent, OSAgent,
            MemoryAgent, AnalysisAgent)
        from voice.pipeline   import VoicePipeline
        from api.main         import start_api
        from rag.lightrag_setup import build_research_rag
        
        console = Console()
        
        async def main():
            console.print("[cyan]⬡  L.O.R.A. v1.0 — INITIALIZING[/]")
        
            kg  = KGClient()
            llm = LLMRouter()
            rag = await build_research_rag("./data/lightrag_working")
        
            agents = {
                "research" : ResearchAgent(kg, llm, rag),
                "code"     : CodeAgent(kg, llm),
                "docker"   : DockerAgent(kg, llm),
                "database" : DatabaseAgent(kg, llm),
                "git"      : GitAgent(kg, llm),
                "file"     : FileAgent(kg, llm),
                "os"       : OSAgent(kg, llm),
                "memory"   : MemoryAgent(kg, llm),
                "analysis" : AnalysisAgent(kg, llm)
            }
        
            orch  = Orchestrator(agents, kg, llm)
            voice = VoicePipeline(orch)
        
            console.print("[green]✓  All agents online. Voice active.[/]")
            await asyncio.gather(
                start_api(orch, kg),        # FastAPI on :8000
                voice.run_loop()             # Wake word listener
            )
        
        if __name__ == "__main__":
            asyncio.run(main())PYTHON
